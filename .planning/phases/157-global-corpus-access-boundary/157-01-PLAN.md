# Plan 157-01 - Global Access Contract and Route Scoping

## Goal

Make the human-quality corpus access contract global-by-default for platform owners while preserving explicit workspace-scoped behavior for authorized workspace admins and existing callers.

## Context

Use `.planning/phases/157-global-corpus-access-boundary/157-CONTEXT.md` as the source of truth. The key decisions are: no new global routes, no `workspaceId` required for platform-owner global mode, backward compatibility when `workspaceId` is provided, generic 403 for denied global access, and compact segmented control in the existing `HumanQualityCorpusPanel`.

## Acceptance Criteria

- Platform owner can call `GET /api/feedback/human-quality-corpus` without `workspaceId` and receive a global response shape.
- Existing `GET /api/feedback/human-quality-corpus?workspaceId=...` remains workspace-scoped and backward compatible.
- Non-owner users cannot access global corpus data and receive generic `403 forbidden`.
- Workspace admins can only use explicitly scoped workspace access if the route/service permits their scoped access; they cannot fall through to global.
- `HumanQualityCorpusPanel` defaults to Global for platform owner and offers a compact Global/Workspace segmented control.
- Workspace mode keeps the existing Workspace ID input; global mode does not show a blocking Workspace ID requirement.
- Global empty state is short and operational, noting candidate capture comes in Phase 158.

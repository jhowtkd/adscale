# Plan 190-01 - Guided Flow Telemetry Foundation

## Goal

Add a safe telemetry foundation for guided assistant journeys so both paths can be audited by workspace, client profile, thread, path, step, blocker and lifecycle event.

## Context

Phase 190 should not build the owner funnel UI. It creates the event model, repository/query layer, sanitizer and server-side instrumentation needed by Phase 191. Use the existing beta analytics implementation as a pattern for event allowlists and safe JSON, but keep guided-journey telemetry in a dedicated table because Phase 190 requires deterministic scope by guided flow, thread, path and step.

### 190-01-02 - Define safe event contract and metadata sanitizer

**Requirements:** TEL-01, TEL-02, TEL-03

<task>
Create `app/src/server/assistant/guided-flow-telemetry.ts` with the server-side event contract:
- event keys: `guided_flow_started`, `guided_step_viewed`, `guided_input_supplied`, `guided_action_blocked`, `guided_action_proposed`, `guided_action_confirmed`, `guided_action_failed`, `guided_flow_completed`
- blocker categories: `missing_asset`, `missing_references`, `missing_brief_fields`, `action_failure`, `validation_error`, `provider_failure`, `unknown`
- allowed metadata keys only: counts, booleans, short reason codes, safe action type, status and ids already represented in explicit columns

Reject or strip denied payload keys using the existing persistence-denylist behavior. Never persist provider reasoning, signed URLs, raw tool arguments, prompts, model messages or tool evidence. Event recording failures must be observable in server logs but must not block the user journey.
</task>

### 190-01-03 - Instrument guided-flow lifecycle routes

**Requirements:** TEL-01, TEL-03

<task>
Record lifecycle events from existing guided-flow server routes:
- start path: record `guided_flow_started` and the first `guided_step_viewed`
- step/status patch: record `guided_step_viewed` on step change and `guided_flow_completed` on completion
- `Já tenho peça`: record `guided_input_supplied` for selected/uploaded asset and `guided_action_blocked` with `missing_asset` where applicable
- `Produzir do zero`: record `guided_input_supplied` for references/brief updates and `guided_action_blocked` with `missing_references` or `missing_brief_fields`
- action proposal/confirmation/failure points: record proposed, confirmed and failed events where the route already has safe action context

Keep instrumentation server-side; do not expose a public client event ingest endpoint in this phase.
</task>

## Must Haves

- Dedicated telemetry table for guided-flow events.
- Query support by safe scope and time window.
- Events include workspace, clientProfile, thread, path and step.
- Events distinguish `existing_creative` and `from_zero`.
- Safe blocker categories are explicit and queryable.
- Denied payloads are rejected or stripped before persistence.
- Telemetry failure does not break the guided assistant journey.
- Drizzle migration journal is updated with migration 0059.

# Plan 49-01: Beta access and credit entitlements

## Goal

Make monetization coherent by separating internal provider-token cost accounting from user-facing credits/ads, and add beta tester access that allows exactly 10 generated ad outputs without Stripe.

## Must Haves

- Beta access does not create fake Stripe customers or subscriptions.
- A beta workspace can generate ads through the same server spend gate used by paid workspaces.
- The beta allowance is capped at 10 generated ad outputs.
- Paid subscription behavior and Stripe webhook credit grants remain compatible.
- Settings/billing UI distinguishes beta access from paid subscription and does not present raw provider tokens as the user-facing entitlement.
- Tests cover beta allowed, beta exhausted, no active access, active paid access, and idempotent usage.

## Implementation Notes

- Keep `CREDIT_COSTS.image_derivation = 5` unless execution discovers a strong reason to migrate all paid-plan math in the same slice.
- Model beta's 10 ads as 50 internal credits, but display "10 ads" or remaining ads to testers.
- Add an entitlement/access abstraction rather than overloading `subscriptions`.
- Prefer using `creditGrants.source = "beta_tester"` for the spend ledger and a separate entitlement/redemption record for access status and auditability.
- Use a server-side redemption path. A practical MVP is a beta code captured during signup/onboarding, validated by the server, and redeemed once per workspace/user.

## Residual Risks

- The exact beta distribution UX may need one product decision: signup code field versus invite-style redemption link.
- If paid plans also need to become "ads/month" instead of "credits/month", do that as a later pricing-copy phase after beta is working.
- Provider pricing can change; keep pricing assumptions isolated in `pricing-model.ts` and avoid hard-coding provider-token economics into entitlements.

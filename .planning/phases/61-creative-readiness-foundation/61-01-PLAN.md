<task type="auto">
  <name>Task 1: Add typed readiness normalizer</name>
  <files>app/src/server/ai/creative-readiness.ts, app/src/server/ai/creative-readiness.test.ts</files>
  <action>
    Add a small server module that converts `PreflightResult` plus campaign/brand context into a UI-facing `CreativeReadinessResult`.

    Required shape:
    - `overallScore: number`.
    - `status: "ready" | "needs_attention" | "blocked"`.
    - `dimensions[]` with stable ids for `offerClarity`, `textLegibility`, `visualHierarchy`, `ctaProminence`, `brandFit`, and `platformFit`.
    - `blockingIssues[]` separate from `suggestions[]`.
    - `source` metadata with `campaignId`, `assetId`, optional `analyzedAt`, and `preflightStatus`.
    - `canGenerate: boolean` where blocked readiness does not silently queue generation in later phases.

    Mapping guidance:
    - Use `preflight.breakdown.textLegibility` for text legibility.
    - Use `preflight.breakdown.visualHierarchy` for visual hierarchy and offer clarity fallback.
    - Use `preflight.breakdown.ctaProminence` for CTA prominence.
    - Use `preflight.breakdown.brandConsistency` for brand fit.
    - Use `preflight.breakdown.platformReadiness` for platform fit.
    - Treat score under 50 or critical issue as blocking; 50-69 as needs attention; 70+ as ready.
    - Do not claim to validate post-generation information preservation.
  </action>
  <verify>cd app && npm test -- src/server/ai/creative-readiness.test.ts</verify>
  <done>
    Unit tests prove ready, needs_attention, blocked, missing-brief, and critical-issue mappings.
  </done>
</task>

<task type="auto">
  <name>Task 2: Extend preflight route with readiness result and explicit rerun</name>
  <files>app/src/app/api/campaigns/[id]/assets/[assetId]/preflight/route.ts, app/src/app/api/campaigns/[id]/assets/[assetId]/preflight/route.test.ts</files>
  <action>
    Extend the existing preflight endpoint so both GET and POST can return `readiness` next to `preflight`.

    Required behavior:
    - GET returns cached `readiness` whenever cached `preflight` metadata is valid.
    - POST computes readiness after analysis succeeds.
    - Add an explicit rerun control, such as request body `{ "force": true }` or query `?force=1`, to bypass completed cached metadata.
    - Preserve rate limit, workspace membership, campaign existence, asset ownership, stale analyzing reset, and spend gate behavior.
    - Do not spend credits on GET.
    - Do not charge repeated POST if returning cached result without force.
    - Store readiness in asset metadata only if it avoids drift; otherwise compute from stored preflight on read. Prefer the simpler no-drift option unless execution proves performance concerns.
  </action>
  <verify>cd app && npm test -- 'src/app/api/campaigns/[id]/assets/[assetId]/preflight/route.test.ts'</verify>

# Findings: Creative Work `86808294-6bb9-49e0-99ea-d5111c5806f9`

**Date:** 2026-08-01  
**Environment:** production (`adscale.jhonatansoares.com`)  
**Scope:** read-only investigation; no generation was retriggered and no production data was changed.

## Executive summary

The work was accepted by production and charged for five outputs, but it was not complete in the observed window. The generation was progressing sequentially: three of five outputs had completed successfully, the fourth had started, and no failure was observed.

There are two independent user-facing/system problems:

1. An unauthenticated deep link with `workId` is redirected from `/` to the marketing page `/hi`, dropping the query string before the dashboard can hydrate the work.
2. This work used the web/legacy image path with an account-wide concurrency limit of one. The dedicated image worker is declared in `render.yaml` but was absent from the live Render service inventory, which is consistent with the observed queue slowness. That absence alone does not prove a terminal failure.

## Evidence

### Link and authentication

- `GET https://adscale.jhonatansoares.com/?workId=86808294-6bb9-49e0-99ea-d5111c5806f9` without a session returned `307` to `/hi`.
- The redirected page was the public marketing page. It did not render the dashboard and produced no dynamic `/api` requests in a browser observation.
- `GET /api/creative-work/86808294-6bb9-49e0-99ea-d5111c5806f9` without authentication returned `401 Unauthorized`.
- The dashboard only receives the `workId` after the proxy allows the request; see `app/src/proxy.ts`, `app/src/app/(dashboard)/dashboard-search-params.ts`, and `app/src/components/dashboard/DashboardHomeActions.tsx`.

### Generation lifecycle

Production logs on `adscale-app` showed:

- `18:41:46.261Z`: `creative_work_generation_requested`, five units, 25 credits.
- `18:41:46.741Z`: `creative_work_generation_dispatched`, result `sent`.
- `18:41:46.761Z`: `creative_work_generation_accepted`, five output IDs.
- `18:52:03.801Z` and `18:52:48.489Z`: first two outputs completed.
- `18:58:16.614Z`: third output completed successfully.
- `18:58:16.775Z`: aggregate recorded `terminalCount=3`, `successCount=3`, `failureCount=0`, result `partial`.
- `18:58:17.455Z`: fourth output entered the queue; `generate_base` started at `18:58:17.710Z`.

The latest queried log window ended at `19:01:55Z`; it contained no terminal event for the fourth or fifth output. This proves partial progress, not final completion.

### Queue and deployment

- `app/src/server/jobs/creative-work.ts` configures `generate-creative-work-output` with account-wide concurrency `limit: 1`.
- The observed outputs used the `legacy` protocol and three provider calls per output, so sequential execution produces multi-minute waits.
- Live Render inventory contained `adscale-app`, but no separate `adscale-image-worker` Render service, although `render.yaml` declares that worker. The presence of the worker function in source is not proof that it is registered live.
- The live build was `a69c9b690301fa47ed6d5abc82bf5d51890ca19f`; `/api/health` returned 200. Health confirms service availability, not generation completion.

## Root-cause assessment

### Confirmed: deep-link query loss

`redirectUnauthenticated()` in `app/src/proxy.ts` sends anonymous `/` requests directly to `MARKETING_URL`. The redirect does not preserve `request.nextUrl.search`, so `workId` is lost. Existing tests cover plain `/`, but not `/?workId=...`.

### Confirmed for latency: serialized processing on the web path

The observed work used the legacy event path, whose job config is account-wide serial. The live infrastructure does not show a separate `adscale-image-worker` Render service, so the deployment does not satisfy the intended worker split. This explains the long queue and partial state, but the logs prove that the jobs were executing; they do not prove that the missing worker caused a terminal failure. The repository also contains a v2 worker path with a different concurrency configuration, so its live registration must be verified before changing routing.

### Not confirmed for this work: client-side false timeout

`apiFetch` has a 15-second default timeout, while preparation can await copy generation. This can create a false error in the composer while the server continues. However, this work reached `generation_accepted`, so that timeout is not sufficient evidence of the backend dispatch failure here. It remains a separate reliability fix.

## Independent second opinion

An independent read-only review confirmed:

- The proxy query-loss bug, expected `401` without authentication, serial web-path job, `3/5` progress, and 15-second timeout hypothesis.
- The worker absence should be treated as a latency/infrastructure hypothesis until live worker registration and Inngest function presence are verified.
- The timeout is a possible client-side symptom, not the cause of this work reaching `generation_accepted`.
- The next order should be: inspect the same authenticated work, fix the deep link, verify/provision the worker, measure before increasing concurrency, then scope the timeout change.

The reviewer also flagged that the local checkout is `cf9a6090`, while production reports build `a69c9b69`. `origin/main` was compared for the proxy and queue snippets; full live-source equivalence remains unverified.

## Recommended changes

### 1. Preserve application deep links through authentication

In `app/src/proxy.ts`, keep the current marketing redirect for plain anonymous `/`, but route `/` requests containing `workId` to login with an internal callback containing the original path and query. Add a regression in `app/src/proxy.test.ts` asserting that `/?workId=<uuid>` does not redirect to `/hi` and that the callback preserves the query.

This is the smallest safe fix because it changes only deep links and leaves the public landing-page behavior unchanged.

### 2. Restore the dedicated image worker

Provision `adscale-image-worker` in Render and configure it with `IMAGE_JOB_TARGET=worker`. Verify that the worker connects to Inngest and that new heavy-image events execute on the worker before changing concurrency.

### 3. Tune concurrency only after worker validation

Keep the current limit of one until worker health, memory, provider limits, and queue latency are measured. Then raise concurrency incrementally, with rollback criteria for RSS growth, restarts, provider rate limits, or duplicate settlement.

### 4. Remove the slow-action false timeout

Give only the preparation/generation mutations an explicit longer timeout using the existing client mechanism, translate aborts into a user-facing recovery message, and test the real composer-to-generation handoff. Do not increase the global API timeout.

### 5. Handle the current work safely

Do not submit `action=initial` again: five outputs were already accepted and charged. Reopen the original link after authenticating and inspect the existing outputs. Retry only an output that is actually terminally failed and eligible for the existing retry/refund policy.

## Verification plan

1. Unit test the anonymous `/?workId=...` proxy path.
2. Browser check: anonymous link → login → dashboard opens the same work and successfully fetches its detail API.
3. For this work, confirm an aggregate with `terminalCount=5`, `successCount=5`, and `failureCount=0`, then confirm all five outputs in the UI.
4. After worker provisioning, verify logs move from `adscale-app` to `adscale-image-worker` and measure queue wait before increasing concurrency.
5. Exercise a preparation longer than 15 seconds and verify there is no false failure or duplicate charge.

## Limitations

- The user session was not accessed; the unauthenticated link behavior was reproduced with a clean browser session.
- Direct production database inspection was unavailable because Render PostgreSQL rejected the current IP via its allowlist. The completion assessment above is based on live application logs and HTTP/browser evidence.
- The local checkout is not the live build commit. Proxy and queue snippets were compared against `origin/main`; full production source equivalence was not established.
- No paid production generation was used as a diagnostic probe.

## Decision

The immediate safe action is to fix deep-link preservation and restore the declared worker separately. Do not rerun this work while its accepted outputs are still processing.
